# dotagents

Personal instructions, skills, MCP servers, and selected app settings for Cursor, Zed, Claude Code, and GitHub Copilot.

## Layout

- `plugins/<name>/` — dotagents plugins. Each holds any of `rules/*.md`, `skills/<name>/SKILL.md`, `scripts/`, and `mcp/*.json`. See [Plugins](#plugins).
- `plugins/dotagents-defaults/` — the built-in plugin: canonical, always-on rules (one section per file, joined in filename order after `introduction.md`) and reusable skills. It's the only plugin committed to this repository.
- `AGENTS.md` — generated by `install.sh` from every plugin's `rules/`. Git ignores it; don't edit it by hand.
- `settings/claude.json` — selected Claude Code settings enforced on install.
- `settings/copilot.json` — selected GitHub Copilot settings enforced on install.
- `install.sh` — the entry point. It checks for Node, installs dependencies when needed, then runs `scripts/install.ts`.
- `scripts/install.ts` — generates `AGENTS.md`, then installs compatibility links, adapters, plugin skills and scripts, plugin MCP servers, and selected settings in each agent's global configuration.
- `scripts/settings.ts` — applies a strict JSON settings overlay with minimal edits, safe writes, and backups.
- `scripts/mcp/` — applies plugin MCP servers to each agent's config. See [MCP servers](#mcp-servers).
- `scripts/lib/` — JSON parsing, file snapshots and atomic replacement, and minimal JSON edits, shared by settings and MCP servers.
- `tests/` — unit and installer tests using temporary configuration directories.
- `action.yml` — a composite action that installs dotagents on a CI runner. See [On a runner](#on-a-runner).
- `docs/best-practices.md` — conventions for changing this repository. Read it first.

Edit a rule, a skill, or a settings overlay in this repository, then commit the change normally. Put rules, skills, and scripts that don't belong in the defaults, such as which GitHub account to use or a skill that posts to a team's chat channel, in another plugin instead. Installed links and adapters are installation details; app settings files also retain locally managed values.

## Plugins

A plugin is a folder under `plugins/` with any of these:

- `rules/*.md` — appended to `AGENTS.md` in filename order, with `introduction.md`, if any, first.
- `skills/<name>/` — linked into each agent's skills folder.
- `scripts/*` — executable files linked into `~/.agents/bin/` (or `$AGENTS_HOME/bin/`). Rules and skills call them there, such as `~/.agents/bin/gh-as`, so the path is the same for every plugin and machine. Non-executable files are skipped.
- `mcp/<name>.json` — an MCP server, added to every selected agent's config. See [MCP servers](#mcp-servers).

`dotagents-defaults` always loads first, then every other plugin in name order. Two plugins can't provide a skill, script, or MCP server with the same name; the installer fails before changing anything.

Git ignores every plugin except `dotagents-defaults`, so each one can be its own repository:

```sh
# Private plugin with its own history, never pushed anywhere
mkdir -p plugins/local/rules && git -C plugins/local init

# Shared plugin, such as one for a team
git clone git@github.com:example/team-agents.git plugins/team
```

Rerun `./install.sh` after adding, removing, or editing a plugin. Removing a plugin doesn't remove links it installed earlier; delete those by hand. MCP servers are the exception: the installer removes ones no plugin declares anymore.

## Install

The installer requires Bash, Node 22.18 or later, and `npm`. Node runs the installer's TypeScript directly, with no build step. `./install.sh` runs `npm ci` itself the first time, and again whenever `package-lock.json` changes.

Install support for all four agents:

```sh
./install.sh
```

Install only selected agents:

```sh
./install.sh cursor zed
./install.sh claude copilot
```

The installer configures:

| Agent          | Standing instructions                        | Skills                                       | MCP servers                                        |
| -------------- | -------------------------------------------- | -------------------------------------------- | -------------------------------------------------- |
| Cursor         | Generated at `~/.cursor/rules/dotagents.mdc` | Linked individually into `~/.agents/skills/` | `~/.cursor/mcp.json`                               |
| Zed            | `~/.config/zed/AGENTS.md` symlink            | Linked individually into `~/.agents/skills/` | `context_servers` in `~/.config/zed/settings.json` |
| Claude Code    | `~/.claude/CLAUDE.md` symlink                | Linked individually into `~/.claude/skills/` | `~/.claude.json`                                   |
| GitHub Copilot | `~/.copilot/copilot-instructions.md` symlink | Linked individually into `~/.agents/skills/` | `~/.copilot/mcp-config.json`                       |

Every run first regenerates `AGENTS.md`, starting it with a marker comment. The installer refuses to replace an `AGENTS.md` without that marker, so move hand-written instructions into a plugin's `rules/` before installing. Cursor requires `.mdc` frontmatter, so its adapter is also regenerated from `AGENTS.md`. Zed, Claude Code, and Copilot use the generated file directly through symlinks. The Copilot integration covers Copilot CLI and the Copilot agent in VS Code, which share `~/.copilot`.

Existing user-managed instruction files, skill folders, and scripts are never overwritten. The installer checks for all of them, along with settings and MCP conflicts, before changing anything. Skills are linked one directory at a time so unrelated skills can coexist in each destination.

## Configuration

Override an agent's configuration directory with `CURSOR_HOME`, `ZED_HOME`, `CLAUDE_HOME`, `COPILOT_HOME`, or `AGENTS_HOME`:

```sh
ZED_HOME="$HOME/custom-zed" ./install.sh zed
```

Run the installer again after editing a rule, adding a skill or plugin, or editing a settings overlay. Agents only see rule changes once `AGENTS.md` is regenerated.

## On a runner

This repository is also a GitHub or Gitea Actions action. It installs dotagents into temporary homes under `$RUNNER_TEMP` and exports their paths, such as `COPILOT_HOME`, to later steps. Agents those steps run, such as a review bot using the Copilot CLI, then follow these instructions and settings. Put it before the step that runs the agent:

```yaml
- uses: https://github.com/KurtPreston/dotagents@main
  with:
    targets: copilot # the default; any of cursor, zed, claude, copilot
```

The runner needs Node 22.18 or later, for example from `actions/setup-node` in an earlier step. The action runs `./install.sh --runner`, which you can also run yourself. It requires `RUNNER_TEMP` and `GITHUB_ENV`, and installs `copilot` unless you name other targets.

## App settings

When Claude is selected, the installer merges `settings/claude.json` into `$CLAUDE_HOME/settings.json` (normally `~/.claude/settings.json`). It does **not** symlink that file. The overlay disables commit and PR attribution text and session links, and opts out of nonessential data sent to Anthropic:

```json
{
  "attribution": {
    "commit": "",
    "pr": "",
    "sessionUrl": false
  },
  "env": {
    "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1",
    "DISABLE_FEEDBACK_COMMAND": "1"
  }
}
```

`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` turns off usage metrics, error reports, and session quality surveys (and feature-flag evaluation, which can make Remote Control unavailable). `DISABLE_FEEDBACK_COMMAND` stops `/feedback`, `/bug`, and `/share` from uploading transcripts. Neither changes how long Anthropic retains prompts sent to the model; see the [Claude Code data usage docs](https://code.claude.com/docs/en/data-usage).

The explicit object form avoids the newer `"attribution": false` shorthand, which requires Claude Code v2.1.281+. See the [Claude Code attribution reference](https://code.claude.com/docs/en/settings-reference#attribution). These are user settings; higher-precedence project or managed settings can override them, and local user settings do not automatically reach cloud sessions.

When Copilot is selected, the installer merges `settings/copilot.json` into `$COPILOT_HOME/settings.json` (normally `~/.copilot/settings.json`), the user settings file shared by Copilot CLI and the VS Code Copilot agent. The overlay stops Copilot from adding a `Co-authored-by: Copilot` trailer to commits:

```json
{
  "includeCoAuthoredBy": false
}
```

Copilot still reads the legacy `~/.copilot/config.json`, and its values win over `settings.json`. If `config.json` sets `includeCoAuthoredBy` (or the older `include_coauthor`), remove it there. Some Copilot modes, such as ACP, have ignored this setting, so the attribution rule in `plugins/dotagents-defaults/rules/` also tells Copilot not to add the trailer. VS Code's own `git.addAICoAuthor` setting is separate and defaults to `"off"`; the installer leaves VS Code settings untouched.

### Ownership and merging

- Repository values win for declared settings each time you install; unrelated keys, including nested keys, survive.
- Objects merge recursively. Scalars and arrays replace the previous value; arrays do not concatenate. `null` is a literal value, not a deletion instruction; this is deliberately not JSON Merge Patch (RFC 7396).
- An overlay object conflicting with a local non-object fails with its key path. Resolve the mismatch explicitly before rerunning.
- Removing a key from the overlay stops enforcing it but does not remove the installed value. There is no automatic pruning or uninstall restoration.
- A missing destination is created. Existing empty files, malformed JSON, duplicate keys, nonstandard or out-of-range numbers, invalid UTF-8, non-object roots, and symlink destinations (including dangling links) are rejected.
- Settings are validated as JSON, not against the application's settings schema. Keep app-specific values compatible with the versions you use. Do not commit secrets in overlays.

Only strict JSON settings for Claude and Copilot are supported. Cursor, Zed, and VS Code app settings are untouched. If you add comments to Copilot's `settings.json`, the installer rejects the file instead of discarding them. MCP servers are the one exception: the MCP sync edits `context_servers` in Zed's `settings.json` and keeps its comments.

`scripts/install.ts` maps each overlay to its destination explicitly. Overlays never contain destination paths, and destinations are not inferred from overlay filenames. A future integration should confirm the app's real settings path rather than assume it sits beside the app's instructions directory.

### Backups and recovery

A changed existing file gets a unique sibling backup named `settings.json.<random>.bak`, containing its exact original bytes with owner-only permissions (`0600`). The installer prints the backup path, never configuration values. Backups can contain local secrets: keep them private and remove old ones manually when no longer needed.

The updated JSON is written to a temporary file beside the destination and atomically replaces it, preserving existing permission bits; new settings files use `0600`. Only the overlay's keys change: every other line, including its formatting, stays as it was. A no-op leaves the file's bytes and modification time unchanged and creates no backup.

To undo an update, stop application writes and copy the printed backup over the settings file. This restores the whole pre-install snapshot, including any settings you may have changed afterward. Adjust or remove the repository overlay values before reinstalling, or installation will enforce them again.

Install while the app is not writing settings. The installer detects changes between reading and replacing a file, but this is not a lock against concurrent writes. Invalid targets, missing dependencies, conflicts with user-managed files, and invalid selected settings or MCP configs fail before installation mutations. Later runtime failures return a nonzero status but do not roll back earlier instruction, skill, or settings operations; resolve the failure and rerun.

## MCP servers

A plugin declares each MCP server in its own `mcp/<name>.json`, once for every agent. The filename is the server's name, which must match `[a-z0-9][a-z0-9_-]*`:

```json
{
  "command": "npx",
  "args": ["-y", "mcp-remote@0.1.38", "https://mcp.linear.app/mcp", "3119"],
  "env": {}
}
```

- `command` is required. `args`, a list of strings, and `env`, an object of strings, are optional, as are `load` and `tools`, described below. Any other key, such as `url`, is rejected, so only servers an agent launches as a local process are supported. That process may itself connect to a hosted server, as `mcp-remote` does.
- `command` should name a program, not where it's installed. A bare name such as `npx` is looked up on the `PATH` of the shell running `./install.sh`, and agents get the absolute path, since GUI apps may not inherit your shell's `PATH`. After switching version managers, rerun the installer to update every server. A bare name that isn't on `PATH` fails the install before anything changes, so run the installer from a terminal that has every command.
- `command` may instead be an absolute path, or start with `~/`, for programs that aren't on `PATH`.
- Don't put secrets in declarations. Use servers that sign in on their own, such as through OAuth.
- `load` is `"static"` (the default) or `"on-demand"`. Static servers are installed into every agent, so their tool definitions sit in each session's context. On-demand servers aren't installed at all; agents call them through `mcp-call` instead, described below.
- `tools`, an optional list of tool names, limits which tools agents that support it expose. Copilot gets the list as its `tools`, or `["*"]` when it's omitted. Use it to drop tools a static server shouldn't offer, such as write tools.

Each selected agent gets the server in its own shape, in the file shown in the [Install](#install) table. Copilot entries add `"type": "stdio"` and `"tools"`, and Claude Code entries add `"type": "stdio"`.

### On-demand servers

Every tool definition a static server exposes costs context in every session, whether or not it's used. Keep servers you use often static, and make the rest on-demand. Pair each on-demand server with a short skill whose description says when to reach for it, so agents know it exists without loading its tools.

Agents call on-demand servers with `~/.agents/bin/mcp-call`, which starts the declared server, runs one request, and exits:

```sh
mcp-call                                 # list declared servers
mcp-call SERVER --list                   # list a server's tools
mcp-call SERVER --schema TOOL            # print a tool's input schema
mcp-call SERVER TOOL '{"arg": "value"}'  # call a tool and print its result
```

### Ownership

`~/.agents/state/mcp.json` (under `$AGENTS_HOME`) records which servers dotagents installed for each agent:

- Declared servers are added, or replaced when dotagents installed them earlier.
- Servers dotagents installed that no plugin declares anymore are removed. Servers you add by hand are never touched.
- A hand-added server with a declared server's name is adopted if it's identical. Otherwise the installer fails and names it, so remove or rename it first. To take over a hand-added server deliberately, list its name for that agent in the state file.
- Only selected agents are changed. The installer runs the sync when servers are declared or the state file exists, so removing a plugin's last server still cleans up.

### Writes

The sync follows the same safety rules as [app settings](#backups-and-recovery):

- Every selected config is parsed, and every command resolved, before any file changes.
- Only the affected servers' lines change. Comments, formatting, and every other key survive, including the rest of Zed's settings and Claude Code's app state in `~/.claude.json`.
- A changed file gets an owner-only `<file>.<random>.bak` backup and is replaced atomically, keeping its permissions. New files are created owner-only.
- An unchanged file isn't rewritten.
- Malformed files, duplicate keys, and symlinked destinations are rejected.

Claude Code rewrites `~/.claude.json` while it runs, so install with Claude Code closed. The sync refuses to replace a file that changed after it was read, but it can't lock out other writers.

## Development

Read [docs/best-practices.md](docs/best-practices.md) before changing anything. Everything is TypeScript, run directly by Node with no build step:

```sh
npm ci
npm run typecheck
npm run lint
npm run format:check
npm test
bash -n install.sh
```

Tests use temporary homes and configuration-directory overrides, never real application settings. The installer tests run `./install.sh` against a copy of the repository, and are skipped unless `npm ci` has installed dependencies.
