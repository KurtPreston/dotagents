# dotagents

An installer for agent plugins. It gives Cursor, Zed, Claude Code, GitHub Copilot, and Codex one set of standing instructions, skills, scripts, MCP servers, and selected app settings, gathered from plugins that can each live in their own repository.

## Quick start

```sh
git clone https://github.com/KurtPreston/dotagents.git && cd dotagents
./install.sh --add git@github.com:example/team-agents.git   # optional: add a plugin repository
./install.sh
```

To hand teammates a ready-made setup, share a `dotagents.jsonc` listing your team's plugins. They put it in the checkout, then run `./install.sh`.

## Layout

- `plugins/<name>/` — plugins. Each holds any of `rules/*.md`, `skills/<name>/SKILL.md`, `scripts/`, `mcp/*.json`, and `settings/*.json`. See [Plugins](#plugins).
- `plugins/dotagents-defaults/` — the built-in plugin, and the only one committed here: universal rules and skills, such as keeping private details out of public places.
- `dotagents.jsonc` — this machine's list of remote plugins, which every install clones or updates. Git ignores it; see `dotagents.example.jsonc`.
- `AGENTS.md` — generated by `install.sh` from every plugin's `rules/`. Git ignores it; don't edit it by hand.
- `install.sh` — the entry point. It checks for Node, installs dependencies when needed, then runs `scripts/install.ts`.
- `scripts/install.ts` — syncs remote plugins, generates `AGENTS.md`, then installs compatibility links, adapters, plugin skills and scripts, MCP servers, and settings in each agent's global configuration.
- `scripts/agents.ts` — the supported agents, and which are installed on this machine.
- `scripts/plugins/` — reads `dotagents.jsonc` and clones or fast-forwards the plugins it lists.
- `scripts/settings.ts` — merges plugins' settings overlays and applies them with minimal edits, safe writes, and backups.
- `scripts/mcp/` — applies plugin MCP servers to each agent's JSON or TOML config. See [MCP servers](#mcp-servers).
- `scripts/lib/` — plugin discovery, `PATH` lookup, JSON parsing, file snapshots and atomic replacement, and minimal JSON edits.
- `bin/mcp-call` — calls on-demand MCP servers. See [On-demand servers](#on-demand-servers).
- `tests/` — unit and installer tests using temporary configuration directories.
- `action.yml` — a composite action that installs dotagents on a CI runner. See [On a runner](#on-a-runner).
- `docs/best-practices.md` — conventions for changing this repository. Read it first.

Edit a plugin's rules, skills, or overlays in its own folder and commit there. Installed links and adapters are installation details; app settings files also keep locally managed values.

## Plugins

A plugin is a folder under `plugins/` with any of these:

- `rules/*.md` — appended to `AGENTS.md` in filename order. Prefix a file with `_`, such as `_introduction.md`, to put it before every other plugin's rules.
- `skills/<name>/` — linked into each agent's skills folder.
- `scripts/*` — executable files linked into `~/.agents/bin/` (or `$AGENTS_HOME/bin/`). Rules and skills call them there, such as `~/.agents/bin/mcp-call`, so the path is the same for every plugin and machine. Non-executable files are skipped.
- `mcp/<name>.json` — an MCP server, added to every selected agent's config. See [MCP servers](#mcp-servers).
- `settings/zed.json`, `settings/claude.json`, `settings/copilot.json` — app settings overlays. See [App settings](#app-settings).

`dotagents-defaults` always loads first, then the plugins in `dotagents.jsonc` in the order listed, then any other folders in `plugins/` by name. Two plugins can't provide a skill, script, or MCP server with the same name, or set one setting to different values; the installer fails before changing anything. The name `mcp-call` is reserved for the engine.

Rerun `./install.sh` after adding, removing, or editing a plugin. It removes links to skills and scripts that plugins no longer provide, and MCP servers no plugin declares anymore.

### Remote plugins

List plugin repositories in `dotagents.jsonc` at the repository root:

```jsonc
{
  "plugins": [
    { "name": "team", "git": "git@github.com:example/team-agents.git" },
    { "name": "mine", "git": "git@github.com:example/my-agents.git", "ref": "stable" },
  ],
}
```

- `name` is the folder under `plugins/`. `./install.sh --add GIT_URL` appends an entry, naming it after the repository unless you pass `--name`, and creates the file if needed.
- `ref` is a branch or tag to follow. Without it, the plugin follows its remote's default branch.
- Each install clones missing plugins and fast-forwards the rest. A plugin with uncommitted changes, local commits, or a different branch checked out is left alone with a warning, as is one whose fetch fails, so offline installs still work.
- A folder whose `origin` doesn't match its `git` URL fails the install, so fix or remove it first.

Folders in `plugins/` that aren't listed are local-only plugins. Git ignores everything in `plugins/` except `dotagents-defaults`, so a local plugin can be a plain folder or its own repository:

```sh
mkdir -p plugins/local/rules && git -C plugins/local init
```

## Install

The installer requires Bash, Node 22.18 or later, and `npm`. Node runs the installer's TypeScript directly, with no build step. `./install.sh` runs `npm ci` itself the first time, and again whenever `package-lock.json` changes.

Install support for every agent on this machine:

```sh
./install.sh
```

With no agents named, the installer configures each agent it finds installed and prints which it skipped. An agent counts as installed when one of its commands is on `PATH` or, on macOS, its app is in `/Applications` or `~/Applications`:

| Agent          | Commands                           | Apps                                  |
| -------------- | ---------------------------------- | ------------------------------------- |
| Cursor         | `cursor`                           | `Cursor.app`                          |
| Zed            | `zed`, `zeditor`                   | `Zed.app`                             |
| Claude Code    | `claude`                           | `Claude.app`                          |
| GitHub Copilot | `copilot`, `code`, `code-insiders` | `Visual Studio Code.app` and Insiders |
| Codex          | `codex`                            | `Codex.app`                           |

Configuration folders such as `~/.cursor` don't count, since an earlier install may have created them. Skipping an agent leaves anything already installed for it in place.

Name agents to install exactly those, whether or not they're detected:

```sh
./install.sh cursor zed
./install.sh claude copilot codex
```

The installer configures:

| Agent          | Standing instructions                        | Skills                                       | MCP servers                                        |
| -------------- | -------------------------------------------- | -------------------------------------------- | -------------------------------------------------- |
| Cursor         | Generated at `~/.cursor/rules/dotagents.mdc` | Linked individually into `~/.agents/skills/` | `~/.cursor/mcp.json`                               |
| Zed            | `~/.config/zed/AGENTS.md` symlink            | Linked individually into `~/.agents/skills/` | `context_servers` in `~/.config/zed/settings.json` |
| Claude Code    | `~/.claude/CLAUDE.md` symlink                | Linked individually into `~/.claude/skills/` | `~/.claude.json`                                   |
| GitHub Copilot | `~/.copilot/copilot-instructions.md` symlink | Linked individually into `~/.agents/skills/` | `~/.copilot/mcp-config.json`                       |
| Codex          | `~/.codex/AGENTS.md` symlink                 | Linked individually into `~/.agents/skills/` | `mcp_servers` in `~/.codex/config.toml`            |

Every run first regenerates `AGENTS.md`, starting it with a marker comment. The installer refuses to replace an `AGENTS.md` without that marker, so move hand-written instructions into a plugin's `rules/` before installing. Cursor requires `.mdc` frontmatter, so its adapter is also regenerated from `AGENTS.md`. Zed, Claude Code, Copilot, and Codex use the generated file directly through symlinks. The Copilot integration covers Copilot CLI and the Copilot agent in VS Code, which share `~/.copilot`. The Codex integration covers Codex CLI, its IDE extension, and its desktop app, which share `~/.codex`.

Existing user-managed instruction files, skill folders, and scripts are never overwritten. The installer checks for all of them, along with settings and MCP conflicts, before changing anything. Skills are linked one directory at a time so unrelated skills can coexist in each destination.

## Configuration

Set `DOTAGENTS_APP_DIRS` to a `:`-separated list of folders to search for apps instead of the macOS defaults, or to an empty string to detect agents by command alone.

Override an agent's configuration directory with `CURSOR_HOME`, `ZED_HOME`, `CLAUDE_HOME`, `COPILOT_HOME`, `CODEX_HOME`, or `AGENTS_HOME`:

```sh
ZED_HOME="$HOME/custom-zed" ./install.sh zed
```

Run the installer again after editing a rule, adding a skill or plugin, or editing a settings overlay. Agents only see rule changes once `AGENTS.md` is regenerated.

## On a runner

This repository is also a GitHub or Gitea Actions action. It installs dotagents into temporary homes under `$RUNNER_TEMP` and exports their paths, such as `COPILOT_HOME`, to later steps. Agents those steps run, such as a review bot using the Copilot CLI, then follow the installed instructions and settings. Put it before the step that runs the agent:

```yaml
- uses: https://github.com/KurtPreston/dotagents@main
  with:
    targets: copilot # the default; any of cursor, zed, claude, copilot, codex
    config: .github/dotagents.jsonc # optional: remote plugins to install
    token: ${{ secrets.PLUGINS_TOKEN }} # optional: read access to private plugin repositories
```

- `config` is a `dotagents.jsonc`, relative to the workspace. Without it, the runner gets only `dotagents-defaults`.
- `token` lets git clone private plugins from the server the workflow runs on. SSH URLs for that server are cloned over HTTPS with the token, for the install step only.

The runner needs Node 22.18 or later, for example from `actions/setup-node` in an earlier step. The action runs `./install.sh --runner`, which you can also run yourself. It requires `RUNNER_TEMP` and `GITHUB_ENV`, and installs `copilot` unless you name other targets.

## App settings

Plugins can enforce selected app settings with overlays in `settings/`. Each selected agent gets every plugin's overlay for it merged into its settings file:

| Overlay                 | Destination                                                         | Format |
| ----------------------- | ------------------------------------------------------------------- | ------ |
| `settings/zed.json`     | `$ZED_HOME/settings.json` (normally `~/.config/zed/settings.json`)  | JSONC  |
| `settings/claude.json`  | `$CLAUDE_HOME/settings.json` (normally `~/.claude/settings.json`)   | JSON   |
| `settings/copilot.json` | `$COPILOT_HOME/settings.json` (normally `~/.copilot/settings.json`) | JSON   |

Overlays from several plugins merge in plugin order. Two plugins may set different keys of the same object, but setting one key to different values fails the install and names both files. An agent no plugin has an overlay for keeps its settings file untouched. The installer never symlinks settings files. Copilot's `settings.json` is shared by Copilot CLI and the VS Code Copilot agent.

### Ownership and merging

- Overlay values win for declared settings each time you install; unrelated keys, including nested keys, survive.
- Objects merge recursively. Scalars and arrays replace the previous value; arrays do not concatenate. `null` is a literal value, not a deletion instruction; this is deliberately not JSON Merge Patch (RFC 7396).
- An overlay object conflicting with a local non-object fails with its key path. Resolve the mismatch explicitly before rerunning.
- Removing a key from the overlay stops enforcing it but does not remove the installed value. There is no automatic pruning or uninstall restoration.
- A missing destination is created. Existing empty files, malformed JSON, duplicate keys, nonstandard or out-of-range numbers, invalid UTF-8, non-object roots, and symlink destinations (including dangling links) are rejected.
- Settings are validated as JSON, not against the application's settings schema. Keep app-specific values compatible with the versions you use. Do not commit secrets in overlays.

Claude and Copilot settings use strict JSON; Zed settings allow comments and trailing commas (JSONC). Cursor, VS Code, and Codex app settings are untouched; Codex has no overlay, since its settings are TOML. If you add comments to Copilot's `settings.json`, the installer rejects the file instead of discarding them. The MCP sync also edits `context_servers` in Zed's `settings.json` and keeps its comments.

`scripts/install.ts` maps each overlay to its destination explicitly. Overlays never contain destination paths, and destinations are not inferred from overlay filenames. A future integration should confirm the app's real settings path rather than assume it sits beside the app's instructions directory.

### Backups and recovery

A changed existing file gets a unique sibling backup named `settings.json.<random>.bak`, containing its exact original bytes with owner-only permissions (`0600`). The installer prints the backup path, never configuration values. Backups can contain local secrets: keep them private and remove old ones manually when no longer needed.

The updated JSON is written to a temporary file beside the destination and atomically replaces it, preserving existing permission bits; new settings files use `0600`. Only the overlay's keys change: every other line, including its formatting, stays as it was. A no-op leaves the file's bytes and modification time unchanged and creates no backup.

To undo an update, stop application writes and copy the printed backup over the settings file. This restores the whole pre-install snapshot, including any settings you may have changed afterward. Adjust or remove the plugin's overlay values before reinstalling, or installation will enforce them again.

Install while the app is not writing settings. The installer detects changes between reading and replacing a file, but this is not a lock against concurrent writes. Invalid targets, missing dependencies, conflicts with user-managed files, and invalid selected settings or MCP configs fail before installation mutations. Later runtime failures return a nonzero status but do not roll back earlier instruction, skill, or settings operations; resolve the failure and rerun.

## MCP servers

A plugin declares each MCP server in its own `mcp/<name>.json`, once for every agent. The filename is the server's name, which must match `[a-z0-9][a-z0-9_-]*`:

```json
{
  "command": "npx",
  "args": ["-y", "mcp-remote@0.1.38", "https://mcp.linear.app/mcp", "3119"],
  "env": {}
}
```

- `command` is required. `args`, a list of strings, and `env`, an object of strings, are optional, as are `load` and `tools`, described below. Any other key, such as `url`, is rejected, so only servers an agent launches as a local process are supported. That process may itself connect to a hosted server, as `mcp-remote` does.
- `command` should name a program, not where it's installed. A bare name such as `npx` is looked up on the `PATH` of the shell running `./install.sh`, and agents get the absolute path, since GUI apps may not inherit your shell's `PATH`. After switching version managers, rerun the installer to update every server. A static server whose bare name isn't on `PATH` fails the install before anything changes, so run the installer from a terminal that has every command. On-demand servers' commands aren't checked at install, only when `mcp-call` starts them, so a machine can skip programs it never calls.
- `command` may instead be an absolute path, or start with `~/`, for programs that aren't on `PATH`.
- Don't put secrets in declarations. Use servers that sign in on their own, such as through OAuth.
- `load` is `"static"` (the default) or `"on-demand"`. Static servers are installed into every agent, so their tool definitions sit in each session's context. On-demand servers aren't installed at all; agents call them through `mcp-call` instead, described below.
- `tools`, an optional list of tool names, limits which tools agents that support it expose. Copilot gets the list as its `tools`, or `["*"]` when it's omitted, and Codex as its `enabled_tools`. Use it to drop tools a static server shouldn't offer, such as write tools.

Each selected agent gets the server in its own shape, in the file shown in the [Install](#install) table. Copilot entries add `"type": "stdio"` and `"tools"`, and Claude Code entries add `"type": "stdio"`. Codex gets each server as a `[mcp_servers.<name>]` table, with `tools` as its `enabled_tools`.

### On-demand servers

Every tool definition a static server exposes costs context in every session, whether or not it's used. Keep servers you use often static, and make the rest on-demand. Pair each on-demand server with a short skill whose description says when to reach for it, so agents know it exists without loading its tools.

Agents call on-demand servers with `~/.agents/bin/mcp-call`, which starts the declared server, runs one request, and exits:

```sh
mcp-call                                 # list declared servers
mcp-call SERVER --list                   # list a server's tools
mcp-call SERVER --schema TOOL            # print a tool's input schema
mcp-call SERVER TOOL '{"arg": "value"}'  # call a tool and print its result
```

### Ownership

`~/.agents/state/mcp.json` (under `$AGENTS_HOME`) records which servers dotagents installed for each agent:

- Declared servers are added, or replaced when dotagents installed them earlier.
- Servers dotagents installed that no plugin declares anymore are removed. Servers you add by hand are never touched.
- A hand-added server with a declared server's name is adopted if it's identical. Otherwise the installer fails and names it, so remove or rename it first. To take over a hand-added server deliberately, list its name for that agent in the state file.
- Only selected agents are changed. The installer runs the sync when servers are declared or the state file exists, so removing a plugin's last server still cleans up.

### Writes

The sync follows the same safety rules as [app settings](#backups-and-recovery):

- Every selected config is parsed, and every command resolved, before any file changes.
- Only the affected servers' lines change. Comments, formatting, and every other key survive, including the rest of Zed's settings and Claude Code's app state in `~/.claude.json`.
- A changed file gets an owner-only `<file>.<random>.bak` backup and is replaced atomically, keeping its permissions. New files are created owner-only.
- An unchanged file isn't rewritten.
- Malformed files, duplicate keys, and symlinked destinations are rejected.
- In Codex's `config.toml`, a server's `[mcp_servers.<name>]` table and its subtables are replaced whole, and the result is parsed again to check nothing else changed. A server written another way, such as with dotted keys, fails the install; rewrite it as a table or remove it.

Claude Code rewrites `~/.claude.json` while it runs, so install with Claude Code closed. The sync refuses to replace a file that changed after it was read, but it can't lock out other writers.

## Development

Read [docs/best-practices.md](docs/best-practices.md) before changing anything. Everything is TypeScript, run directly by Node with no build step:

```sh
npm ci
npm run typecheck
npm run lint
npm run format:check
npm test
bash -n install.sh
```

Tests use temporary homes and configuration-directory overrides, never real application settings. The installer tests run `./install.sh` against a copy of the repository, and are skipped unless `npm ci` has installed dependencies.
